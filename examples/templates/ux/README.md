# UX Screen And Journey Templates

## Purpose And Status

Copyable briefs and an illustrative example for applying
[UX And Screen Design Standards](../../../ux/README.md).

Status: template, with a worked example.

## Operating Context

Production-oriented web application screens, CRUD tasks and registration
journeys. The depth of the record should match the consequence and uncertainty
of the change.

## Prerequisites And Inputs

Identify the task, audience, approved business rules and existing component
conventions. Replace placeholders and label unknowns. Store the result within
the feature specification or link it from the existing issue; avoid a parallel
document that can drift from implemented behavior.

## Secret And Data Handling

Use synthetic people and records. Do not place customer data, credentials or
unnecessary research identifiers in a public brief or screenshot. No runtime
credentials are needed for these Markdown artifacts.

## Validation

Check the brief against the actual interface and
[UX Checklist](../../../ux/ux-checklist.md). Record checks performed, observed
behavior, unresolved assumptions and remaining issues. Template completion is
not evidence that a user can complete the task.

## Operational Limitations And Lifecycle

The example defines hypothetical business rules; do not copy its required
fields, duplicate policy or archive semantics without checking the product.
It is not executable UI or tested usability evidence. The feature owner should
review the brief when task, audience, components or server behavior changes.
